# 求人票エージェント 設計

## 1. 目的

- 求人票を受け取り、決まった項目にまとめる
- 利用者ごとに決めた観点で、ネクストアクションを提案する
- 自分を含む、**知っている複数の人**（チームメンバーなど）が使う

## 2. 機能

| 機能 | 内容 |
|---|---|
| 求人票の読み込み | **DB**（求人IDで取得）、**PDF**（アップロード）、**Web URL**（ページを取得）、**貼り付けたテキスト**の4通り |
| まとめ | どこから来ても同じ項目にそろえる（会社名、職種、雇用形態、勤務地、リモート可否、給与、必須スキル、歓迎スキル、募集背景、締切、出典）。書かれていない項目は空欄にし、推測で埋めない |
| 観点 | 利用者ごとに名前を付けて保存し、選んで使う。チーム共通のテンプレートも用意する |
| ネクストアクション | **最初は提案だけ**。メール送信などの実行は、あとで確認の手順を付けて追加する |

## 3. 構成

```
利用者（Google アカウントでログイン）
   ▼
IAP（許可したアカウントだけを通す）
   ▼
Cloud Run（1つのサービス）
 ├ チャット画面（src/job_posting_agent/static/index.html）
 └ FastAPI（src/job_posting_agent/server.py）
     ├ IAP の署名付きヘッダー（JWT）を検証し、メールアドレスを user_id にする
     └ ADK の Runner でエージェントを呼ぶ
         ├ 求人の読み込みツール（DB／URL）。PDF は Gemini が直接読む
         ├ まとめの保存ツール（出力の型は JobSummary）
         └ 観点のツール（その人の観点とチームのテンプレートだけ）
   ▼
Cloud SQL for PostgreSQL（ADK のセッション、観点、求人のまとめ、求人票）
Vertex AI の Gemini
```

## 4. 使うサービス

| サービス | 判断 | 理由 |
|---|---|---|
| ADK | ✅ 使う | エンジニアがコードで作る |
| Cloud Run | ✅ 使う | 画面とエージェントを1つにまとめて動かす |
| IAP | ✅ 使う | ログイン画面を作らずに、許可した人だけに公開する |
| Cloud SQL | ✅ 使う | セッション、観点、求人のまとめを人ごとに保存する |
| Vertex AI の Gemini | ✅ 使う | APIキーが不要で、送った内容が学習に使われない |
| Model Armor | ✅ 使う | Webページに埋め込まれた指示への対策 |
| Cloud Logging、Trace | ✅ 使う | 問題が起きた会話を追えるようにする |
| Agent Runtime | ⏸ 後で | 今は Cloud Run で足りる。移す条件は 8 に書く |
| Agent Simulation | ⏸ 後で | 求人票のサンプルで精度を確かめたくなったら使う |
| Agent Identity、Registry、Gateway | ⏸ 後で | エージェントが増えたら使う |
| Memory Bank | ❌ 使わない | 観点は設定としてデータベースに保存する |
| Gemini Enterprise アプリ | ❌ 使わない | 組織向けのサービスで、個人では使えない |
| Agent Studio | ❌ 使わない | コードで作るので不要 |

## 5. 認証（キーやパスワードを発行しない）

| 接続先 | ローカル | Cloud Run |
|---|---|---|
| Gemini（Vertex AI） | 自分のアカウント（ADC） | サービスアカウント |
| Cloud SQL | ローカルは SQLite（必要なら自分のアカウントで IAM 認証） | サービスアカウント（IAM 認証） |

- ローカルでは `gcloud auth application-default login` でログインし、`.env` に `GOOGLE_GENAI_USE_VERTEXAI=TRUE` を書く
- サービスアカウントのキー（JSONファイル）は作らない

## 6. 安全のための決まりごと

- **user_id は IAP の JWT を検証して得たメールアドレスだけを使う**。ブラウザから送られた値や、AIが決めた値は使わない
- セッションは必ず `user_id` 付きで取得する。他人のセッションIDを指定されたら 404 を返す
- ツールは `tool_context.user_id` を使って、その人のデータだけを扱う。SQLは決まった形のものだけを実行し、AIにSQLを書かせない
- URL取得では、http／https 以外、ユーザー名付きのURL、グローバルでないアドレス（`localhost`、`10.x.x.x`、`169.254.169.254` など）へのアクセスを禁止する。リダイレクト先も毎回確認する
- 外部から取得した内容（URL、PDF、DB の本文）は「データ」として扱い、中の指示には従わないようにプロンプトで指示する
- 変更系の API（POST／DELETE）は独自ヘッダー `X-Requested-With` を必須にし、他のサイトからの送信（CSRF）を防ぐ
- 人ごとの利用回数に上限を付ける（1インスタンスごとの簡易な制限）。予算アラートも設定する

## 7. 決めたこと（仮）

| 項目 | 決めたこと | 変えるとき |
|---|---|---|
| 求人票のデータベース | 同じ Cloud SQL の `job_postings` テーブルを読む | 別のDBや外部サービスなら、`repository.get_job_posting` を差し替える |
| 求人のまとめの共有 | 本人だけが見られる | 共有するなら、`job_summaries` の検索条件から `owner_id` を外す |
| チャット画面 | ライブラリを使わない自作の画面 | 必要になったらフロントエンドを別に作る |
| PDF の保存 | 会話のセッションに入れる（Gemini が会話の続きでも読めるように） | セッションが大きくなりすぎたら、ADK の Artifacts（Cloud Storage）に移す |

## 8. あとで見直すこと

| きっかけ | やること |
|---|---|
| 会話をまたいで、その人のことを覚えさせたい | Agent Runtime に移し、Memory Bank を使う |
| エージェントが増えた、他の画面からも呼びたい | Agent Runtime に移し、Identity、Registry、Gateway を使う |
| ネクストアクションを実行させたい | 実行前に確認する手順と、実行の記録を付ける |
| 知らない人にも使ってもらう | ログインの仕組み（Firebase Authentication など）、Cloud Armor、利用規約を用意する |
| 会社として Gemini Enterprise を契約した | 自前のチャット画面の代わりに Gemini Enterprise アプリを使う |
| 利用者が増えて、インスタンスが複数になる | 利用回数の制限を、インスタンス間で共有できる仕組み（Memorystore など）に移す |
| テーブルの形を変える | Alembic などのマイグレーションを入れる（今は起動時にテーブルを作るだけ） |
