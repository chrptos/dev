# 0001. バックエンドに疎結合なレイヤードアーキテクチャを採用する

## ステータス
承認済み

## 日付
2026-11-28

## コンテキスト
- 最初のバックエンドは `server.py`、`tools.py`、`repository.py` などを1つのパッケージに並べた、フラットな構成だった（約15ファイル、約1,000行）
- 「どこに何を書くか」「どこから何を呼んでよいか」が決まっておらず、レビューのたびにコード全体を読む必要があった。**レビューが大変**というのが直接のきっかけ
- 具体的には、次のような問題があった
  - 持ち主の確認、回数制限、PDF の確認、題名の設定が `server.py` に、観点の上限がリポジトリに、と決まりごとが散らばっていた
  - API が ADK のセッション（`DatabaseSessionService`）を直接読んでいた
  - AI のツールがリポジトリを直接呼んでいた。HTTP と AI のツールという2つの入口で、決まりごとが守られているかを別々に確かめる必要があった
  - DB の接続をモジュールのグローバル変数で持っていて、テストで差し替えにくかった
- 今後、求人票の入手元（DB／外部サービス）、セッションの保存先（Cloud SQL／Agent Runtime）、認証（IAP／別の仕組み）を変える可能性がある（[design.md](../design.md) の「あとで見直すこと」）
- 開発者は少なく、規模も小さい。構成の重さがそのまま開発の遅さになる

## 検討した選択肢
1. **疎結合なレイヤードアーキテクチャ（採用）**: domain / application / presentation / infrastructure の4層。application がインターフェース（`Protocol`）を持ち、infrastructure がそれを実装する（依存性の逆転）。presentation と infrastructure は同じ高さでお互いを知らず、`main.py` だけが組み立てる。約25ファイル（実際は約30）
2. **現状のフラットな構成のまま**: ファイルを増やさずに済む — レビューの負担が減らず、決まりごとの置き場所が決まらないままになるため採らなかった
3. **ヘキサゴナルアーキテクチャ（ポートとアダプター）**: 考え方は採用案とほぼ同じ — 層の名前（ポート、アダプター）がチームになじみにくく、「どの層に置くか」をレビューで説明しにくいため、同じ依存の向きをレイヤードの名前で表すことにした
4. **クリーンアーキテクチャ（4つの円に忠実）**: ユースケースごとの入力と出力の型、プレゼンター、コントローラー、ゲートウェイを分ける。約50ファイル — 約1,000行の規模に対して重く、小さな変更でも4つの層を触ることになり、似た型が並んでかえってレビューが大変になるため採らなかった。依存の向きや「ADK を外側に置く」考え方は採用案に取り入れた

## 決定
バックエンドを、依存性の逆転を使った4層の疎結合なレイヤードアーキテクチャで書き、層の向きを import-linter とテストで機械的に確かめる。

## 理由
- **レビューのしやすさ**：差分がどの層にあるかで、確かめることが決まる（例：`application/` の差分なら決まりごと、`infrastructure/` の差分なら SQL と外部との接続）。層の向きの違反はテストで落ちるので、レビューで探さなくてよい
- **決まりごとが1か所に集まる**：持ち主の確認、上限、回数制限はサービスに置く。HTTP から来ても AI のツールから来ても、同じサービスを通るので同じように守られる
- **AI エージェントの扱いがはっきりする**：指示文とツールは「AI にとっての入口」として presentation に、ADK の Runner とセッションは infrastructure に置く。必ず守る決まりは指示文ではなくサービスに書く、という線引きができる
- **差し替えやすさ**：入手元、セッションの保存先、認証は infrastructure の差し替えで済む。サービスのテストは偽物（`tests/fakes.py`）で書け、DB も AI も要らない
- **重さが規模に見合う**：クリーンアーキテクチャの半分ほどのファイル数で、依存の向きという一番効く部分は同じように得られる

## トレードオフ・リスク
- **ファイルが増える**：約15 → 約30。小さな機能を足すときも、domain・application・infrastructure・presentation・main と複数のファイルを触ることが多い
- **サービスが薄い中継になりやすい**：`SummaryService` のように、ほぼリポジトリを呼ぶだけのサービスがある。「決まりごとがないなら層を飛ばしてよい」という例外を作ると構成が崩れるので、薄くても通す
- **import-linter で書けない決まりがある**：外部パッケージの一部（`google.adk.sessions` など）は禁止の対象にできない。ADK の Runner とセッションを infrastructure の外で使わないことは、`tests/test_architecture.py` の自前のチェックで確かめている。このチェックは import 文しか見ないので、動的な import はすり抜ける
- **ADK のセッションを会話の保存先として使い続けている**：`ConversationStore` の裏に隠したが、会話の形（イベントからメッセージへの変換）は ADK の形式に依存している。Agent Runtime に移すときは、この変換も作り直す必要がある
- **domain の型に pydantic を使っている**：`JobSummary` は AI のツールの引数の形にもなっているため、domain に pydantic を許している。pydantic の大きな変更があると domain まで影響する
- **見直す条件**：エージェントやユースケースが増えて1つのサービスが大きくなったら、ユースケースごとにクラスを分ける（クリーンアーキテクチャ寄りにする）ことを検討する。逆に、機能がほとんど増えないまま層が負担になるなら、構成を緩めることを検討する

## 影響範囲
- `backend/src/job_posting_agent/` のすべてのモジュール（置き場所と import の向きを変えた。処理の内容と API の形は変えていない）
- 起動のエントリポイントが `job_posting_agent.server:create_app` から `job_posting_agent.main:create_app` に変わる（Dockerfile、`.claude/launch.json`、README を更新）
- テストを層ごとのディレクトリに分け、サービスの単体テストと層の向きのテストを足した
- 今後の開発：新しい機能は [backend-architecture.md](../backend-architecture.md) の「新しい機能を足すときの手順」に沿って書く。AI に書かせるときは `backend/CLAUDE.md` の決まりに従わせる
- フロントエンドへの影響はない（API の形は変えていない）
